Rename and delete update every name in one place. Daemon applies the events.

Problem. The override and detected game live on Daemon, while the stack lives on DaemonState. So rename_profile can't keep its promise to update “every reference”. Rename or delete a manually loaded profile, and the next tick writes the desktop profile.

Solution. Move the override and the detected game into DaemonState, behind observe and request. decide becomes an internal seam and keeps its 11 tests.

  • locality: every profile name in one module
  • the rename bug fixed by construction
  • tests stop setting daemon._manual_override
  • the misleading rename test becomes honest
  • one notion of “the current game”
[VERIFY] decide deliberately drops a Load made while no game is running, and its docstring says so. Yet Load returns true, and the window says “Loaded X.” (window.py:692–697). Is a desktop Load meant to be refused, or honoured? Once one module owns this, request() can say which.

Consistent with ADR-0001: the slot rules are unchanged.

Problem. DaemonUnavailable is raised only when the session bus is down. The ordinary case is a bus that is up with the daemon stopped. That reaches callers as a bare RuntimeError with the D-Bus error name dropped. The test fakes a failure that production never produces.

Solution. Map ServiceUnknown and NameHasNoOwner to DaemonUnavailable in the client's one call path. Test it with a reply that carries that error name.

  • the error mode joins the interface
  • both callers fixed at once
  • ~10 lines, one honest test

Problem. The tray's docstring says the daemon “announces every change”, but config changes aren't announced. After a create, rename or delete, the tray's menu stays stale for up to 30 seconds. The window works around this by polling every 2 seconds. There are also two decoders for the same state: state() and get_view.

Solution. Every config change and reload emits one signal. Delete client.state() in favour of get_view. The window drops its poll.

  • leverage: one read, two callers
  • delete a 4-round-trip decoder
  • the tray's premise becomes true
  • the window's 2 s poll goes

Follows ADR-0004: the daemon is the only writer, so it is the natural one to announce changes.

Top recommendation

Give the target profile one owner

This one has a real behaviour bug (rename or delete of a manually loaded profile writes the desktop profile), plus a test that passes while describing behaviour production lacks. The cause is architectural: the names that rename has to update live in two modules. Do #2 alongside it, so the fix can be tested through Daemon rather than by setting its private fields. #3 is a small, separate win that users will notice.
