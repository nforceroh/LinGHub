2026-11-19 · main @ 2ed1286 (v0.3.0) · scope: the day's hot spots — hardware/, the daemon's mouse handling, version reporting

module seam leakage deep module
Confirmed defect found during the walk. A binding to an unknown key name (KEY_BOGUS) passes config validation, then raises BindingError (a ValueError) on the first write. No catch list in the daemon names it, so it escapes tick() and the run loop: the daemon exits, and because the config still loads, systemd restarts it into the same crash. Reproduced against the real writer over the test fake. Candidate 1 is the structural fix.

Problem. What a failure means is decided by which exception base class it inherits, across five modules. The daemon sorts them again in four except lists whose order matters. Lower modules are written around that list ("not a RuntimeError, which the daemon reads as a lost mouse"), and anything outside it, like BindingError, kills the daemon. Permanent conditions (an unsupported ratbagd API version, two G502s) are reported as "cannot reach the mouse through ratbagd" once, then logged at debug level forever.

Solution. The Mouse seam's interface names a closed set of outcomes: lost (reconnect), refused (keep the mouse, retry), slot unknown (skip), misconfigured (report loudly; retrying won't help). The ratbag adapter translates into that set in one place, and the daemon matches on meaning.

  • locality: the failure policy lives in one module
  • leverage: the daemon learns four outcomes, not ten classes
  • the BindingError crash becomes "refused"
  • tests assert outcomes, not inheritance
  • catch-list order stops mattering

2. Deepen the ratbag Mouse adapter

Strong local-substitutable
  • src/linghub/hardware/writer.py — ProfileWriter, RatbagConnector
  • src/linghub/hardware/ratbag.py — RatbagClient (_property · _method · _call)

After — one module, interface = the Mouse protocol

RatbagClient with public get / set / call

tested through connect() with a fake bus + a fake sysfs

Problem. "The mouse as the daemon sees it" is spread across a class named for writing, a connector with no tests, a node factory that decides whether a connection succeeds, and a client used mainly through its private methods. The ratbagd-lags-the-kernel race is tested in two halves; nothing tests the whole sequence.

Solution. One module whose interface is the daemon's existing Mouse protocol plus connect(). It owns finding the device, confirming the node and checking identity. RatbagClient gets public primitives, so the private trio stops being the real interface.

  • locality: connection rules in one module
  • the race is tested end to end
  • tests stop faking private methods
  • delete the duplicated IsActive scan
  • delete the unused device property
Respects ADR-0010: reads over HID++, writes through ratbagd. ActiveSlotReader and OnboardProfiles stay as they are; both are already deep.

Problem. #4's absence rules are real behaviour, but they live in three Daemon fields changed by three methods with slightly different rules. They can only be tested end to end, alongside the reconnect mechanics.

Solution. A small state module with an injected clock: the daemon reports lost / search failed / found and gets back what to log. Deletion test: Daemon loses three fields and two methods, so the module earns its place.

  • locality: absence rules in one module
  • tests assert decisions, not log counts
  • Daemon interface shrinks

Problem. Only the restart note is shared. Each caller handles both sentinels and maps errors itself, with different catch lists, so the About dialog says "Daemon not running" when the daemon is running but the version read failed. PREDATES_REPORTING = None means any stray None reads as "old daemon".

Solution. version.py owns a small daemon-version value type and one describe(). The client owns the error-to-value mapping, once.

  • leverage: three callers, one rendering
  • fixes the mislabelled About line
  • sentinels stop leaking as None
Keeps ADR-0009's separate Version property; only the client side changes.
