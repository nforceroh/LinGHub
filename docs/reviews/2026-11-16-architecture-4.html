1. Split the daemon's write surface out

Strong in-process

src/linghub/daemon/service.py:202–343 · 49 methods on one class

Before — 49 methods, one class

D-Bus handlers 14 methods
write persistence _apply_and_save etc
device connect + apply 5 methods
tick + detection 2 methods
run loop + startup 2 methods

The three adapter classes forward into this same class.

After — writes behind a seam

Daemon — run loop, device, tick
ProfileWrites — validate, apply, save, roll back
the 3 collaborators — real, not forwarders

The adapters become the implementation, not a shell around it.

Problem

Last review's grouping added three adapter classes that forward into the same 49-method class. The grouping is cosmetic: the complexity did not move, it got a second name. The collaborators have no behaviour of their own.

Solution

Move the request handlers and the write rule into a module that the adapters actually are, leaving Daemon with the run loop, device connection and tick.

Wins

  • locality: the write rule has a home
  • the adapters stop being ceremony
  • Daemon shrinks toward the run loop
  • 49 methods becomes two digests

Problem

The Protocols were written to describe the three collaborators, and nothing imports them. The adapters do not declare that they satisfy them, so a drifted signature would not be caught.

Solution

Either the adapters declare conformance so a mismatch fails at import, or the file goes. A Protocol nobody reads is a comment with a syntax cost.

Wins

  • the interface is checked, not described
  • or: delete 68 lines of unread code
  • locality: one place states the contract

3. Separate slot reasoning from config mutation

Worth exploring in-process

src/linghub/daemon/state.py:75–103, 128–267

Before — two questions, one class

expected_slot · observe_active_slot

"which slot should the hardware be on?"

set_binding · set_leds · create_profile

"what should the config say?"

Both answer through the same needs_write.

After — one question each

config state

profiles, loaded profile, fingerprint

slot reasoning

expected slot, drift, target slot

Problem

DaemonState both mutates the config and reasons about which hardware Slot should be active. The Slot rules — 0 for desktop, 1 for gaming, drift detection — are device knowledge sitting in a class otherwise about config.

Solution

Keep Slot reasoning where the Slot rules are: expected_slot and drift are one question, config mutation is another.

Wins

  • locality: Slot rules in one place
  • ADR-0001 becomes readable as code
  • config mutation testable alone
Consistent with ADR-0001 (profiles load into slot 1); this makes the rule explicit rather than changing it.

4. Move the panel rules out of the widgets

Worth exploring in-process

src/linghub/ui/dpi_panel.py:103–118 · src/linghub/ui/led_panel.py:112–124

Before — rules inside handlers

dpi_panel._on_toggled
"only one default" in a GTK callback
led_panel._duration_to_speed
ms ↔ slider units, inverted
led_panel._sync_sensitivity
which controls an effect enables

All three are testable only through the widget.

After — rules beside the widgets

panel rules

one default · speed conversion · enabled controls

2 callers

Problem

The same shape the window had last week: a rule that does not need GTK lives inside a GTK callback, so the only way to test it is to build the widget. The speed inversion especially — it is arithmetic, not UI.

Solution

Move the rules into a module both panels call, leaving the panels with widget wiring.

Wins

  • two callers: a real seam
  • the speed inversion gets its own tests
  • panels shrink to wiring

Top recommendation

Split the daemon's write surface out

This is the one place where last review's work did not achieve what it intended. The grouping is real but the complexity stayed: three adapters forward into the same 49-method class, so the interface shrank while the implementation did not move. Doing this also makes #2 answerable — the Protocols describe something that does not exist yet.

Checked, deliberately not proposed

  • config.save re-parses to validate before writing. That is deliberate — the alternative is a corrupt config on disk — and the cost is one parse per edit, not per tick.
  • hotspot_editor.py (526 lines) is a one-off authoring tool with no runtime path.
  • diagram.py geometry is pure but has one caller and no bug history. Not worth a seam yet.
  • The seven __new__ test constructions all belong to widgets that genuinely need GTK; the decisions they used to hide are already out.
