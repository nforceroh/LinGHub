Problem

Seventeen call sites hand-write a member name and signature. Nothing checks them against the daemon, and three were wrong during this project's own work.

Solution

One module declares each member with its signature and argument order; client and interface both read from it.

Wins

  • locality: the contract is one file
  • signature drift fails at import
  • leverage: 17 call sites, one declaration
  • the README test already proves the shape

3. One daemon-access module for the tray

Strong in-process

src/linghub/tray.py:86–106, 176–196 · src/linghub/ui/asyncbridge.py

Before — the pattern, twice

_query()

DaemonClient() → connect → state → disconnect

wrapped in asyncio.run inside a thread

_load_thread()

DaemonClient() → connect → load → disconnect

wrapped in asyncio.run inside a thread

The window keeps one injected client instead.

After — one seam

daemon access

connect once · run off-thread · report back

tray · window · status

Problem

The tray builds a client, connects, queries and disconnects in two separate places, each with its own asyncio.run inside a thread. The window does the same job differently.

Solution

One module owns the connect/query/disconnect lifecycle and the off-thread asyncio setup; the tray and the window both call it.

Wins

  • locality: connection lifecycle in one module
  • leverage: three callers, one interface
  • the tray stops re-implementing asyncio setup
  • testable without a GTK loop

4. A mode table for the binding editor

Worth exploring in-process

src/linghub/ui/binding_editor.py:189–225, 278–315

Before — four chains over six modes

_select_initial_mode: dict + special case
_load_initial_value: if / elif × 4
_selected_value: if × 5 + fallback
_current_binding: if × 5 + fallback

Adding a mode means editing four chains.

After — one table

mode → (widget, kind, read)

one row per mode

6 rows

Problem

Six modes are dispatched by four separate conditional chains. Adding the sixth mode this week meant editing all four, and the compiler cannot tell you if you missed one.

Solution

One table mapping each mode to its widget, its stored kind, and how to read its value.

Wins

  • adding a mode is one row
  • locality: mode knowledge in one place
  • the round-trip test covers all modes

5. Deepen the D-Bus adapter past fifteen callbacks

Worth exploring in-process

Every method is a one-line forward.

After — one collaborator

interface
1 object

the daemon

The adapter translates; it does not enumerate.

Problem

Fifteen constructor callbacks, each stored and forwarded. Adding a member means editing the constructor, the assignment block, the method, and every test's fake.

Solution

Pass one collaborator that answers the operations, so the adapter's interface is the D-Bus surface and nothing else.

Wins

  • interface shrinks to the D-Bus surface
  • adding a member touches one place
  • the fake stops mirroring the constructor

Top recommendation

Finish collapsing the write paths

Five of seven paths already use the helper, so this is finishing a job rather than starting one. The two that bypass it are the two that have already drifted — only the LED path validates before applying. Smallest change here, and it removes a rule from three places to one.

Not proposed, and why

  • hotspot_editor.py (526 lines) is a one-off authoring tool, not on any hot path. Deepening it buys nothing.
  • Splitting window.py by responsibility is real, but the decoupling this week removed the worst symptom. Revisit if it grows again.
  • The CLI's seven dispatch branches are not a problem at seven commands.
