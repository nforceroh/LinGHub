1. Make daemon_access keep its promise

Strong in-process

src/linghub/daemon_access.py:30–45

Before — one error for two causes

connect() returns False

→ DaemonUnavailable

action() raises RuntimeError

→ DaemonUnavailable

The docstring says these are distinguishable. They are not.

After — two causes, two errors

connect() returns False

→ DaemonUnavailable

action() raises

→ propagates unchanged

Callers can retry a connection; they cannot retry a bug.

Problem

The module's whole reason for existing is telling "no daemon" from "the call failed", and it collapses both into one exception. A genuine bug inside an action is reported as a missing daemon.

Solution

Only the connect failure raises DaemonUnavailable; anything the action raises propagates as itself.

Wins

  • the interface matches its documentation
  • locality: one place decides what "unavailable" means
  • a real bug stops looking like a missing daemon

2. Lift the window's decisions out of the widget

Strong in-process

src/linghub/ui/window.py:608–620, 435–438, 384–440

Before — 39 methods, one class

construction 6 methods
refresh + rebuild 10 methods
DPI/LED writes 4 methods
profile CRUD + dialogs 9 methods
binding writes 4 methods
selection + loading 5 methods

Tests build it with __new__ and set 11 private fields.

After — decisions behind a seam

window — widgets only
edit target — which profile, pure
write requests — what to send, pure
display model — state → rows, pure

Tests cross a real interface.

Problem

Decisions like "which profile am I editing" and "what does this state look like as rows" are pure functions trapped behind a GTK widget, so the only way to test them is to construct the widget by hand.

Solution

Move the decisions into modules the window calls; leave widget construction, dialogs and idle scheduling where they are.

Wins

  • the interface is the test surface
  • no __new__, no private fields
  • locality: edit-target rules in one module
  • window shrinks toward layout

3. A mode table for the binding editor

Worth exploring in-process

src/linghub/ui/binding_editor.py:189–205, 279–315

Before — four chains, six modes

_select_initial_mode dict + special case
_load_initial_value if / elif × 4
_selected_value if × 5 + fallback
_current_binding if × 5 + fallback

A seventh mode means four edits, plus a page.

After — one table

mode → (widget, kind, read)

one row per mode

6 rows

Problem

Six modes dispatched by four separate chains. Adding the sixth this week meant editing all four, and one was missed — _select_initial_mode briefly referenced an undefined name.

Solution

One table mapping each mode to its widget, its stored kind, and how to read its value.

Wins

  • adding a mode is one row
  • locality: mode knowledge in one place
  • the round-trip test covers all modes

4. Deepen the D-Bus adapter past fifteen callbacks

Worth exploring in-process

src/linghub/daemon/dbus_service.py:36–53

Before — interface ≈ implementation

interface
15 callbacks
implementation
10 pass-throughs

Ten of sixteen methods just forward.

After — grouped collaborators

interface
3 groups
implementation
the daemon

Profile lifecycle · bindings · device settings.

Problem

Fifteen constructor callbacks, ten of them pure forwards. Adding a member means editing the constructor, the assignment block, the method, and every test's fake.

Solution

Group the callbacks into the three natural collaborators the methods already fall into, and pass those.

Wins

  • interface shrinks from 15 to 3
  • the fake stops mirroring the constructor
  • locality: each group owns its members

Top recommendation

Make daemon_access keep its promise

It is a few lines, and it is a correctness bug rather than a tidiness one: the module exists to distinguish "no daemon" from "the call failed", and currently reports both the same way. A real bug inside an action is indistinguishable from a missing daemon, which is exactly the confusion the module was built to remove.

Not proposed, and why

  • hotspot_editor.py (526 lines) is a one-off authoring tool, not on any hot path.
  • buttonmap.py and processes.py have no dedicated test file but are covered through test_ui.py and test_detection.py. Not a gap.
  • The CLI's dispatch branches are not a problem at seven commands.
  • Validation sitting outside _apply_and_save is deliberate: a rejected value should not touch the config at all.
